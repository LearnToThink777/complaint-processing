# Phase 5 — 상태(State) 패턴 검토 → 미적용 결정 (ADR)

> **적용 디자인 패턴: 없음(의도적 미적용).** 이 단계는 코드를 바꾸는 대신, 남은 후보
> 패턴(State·Template Method)을 실제로 검토하고 "지금은 적용하지 않는다"는 결정을
> 근거와 함께 남기는 설계 결정 기록(ADR)이다. 골든 테스트 4건은 그대로 통과(코드 무변경).

## 검토 1 — 상태(State)를 `agent.py`의 `run()`에 적용?
`ComplaintAgent`에는 상태 흐름이 있다:
`접수 대기 → 이관됨 → 처리 중 → 협상 중 → 처리 중 → 종결`.

State 패턴은 "각 상태가 **자기 상태에서의 행동**과 **다음 상태로의 전이**를 스스로 안다"로
캡슐화한다. 그런데 이 프로젝트의 전이는 상태 객체가 스스로 결정하지 않고 `run()`의 선형
스크립트가 순서대로 몰고 간다. 게다가 각 단계의 행동이 이질적이다(검토항목 도출 / 항목 처리 /
유사사례 조회 / 재협상 / 종결 작문) — 공통 인터페이스(예: `handle()`)로 묶으면 억지스럽고,
프레임 생성 순서에 미묘한 차이를 낼 위험(=골든 불변 위반)만 커진다.

**결정: 적용하지 않는다.** 선형·결정론적 워크플로에 State를 씌우는 것은 이득 없이 클래스만
늘리는 오버엔지니어링이다. 이벤트로 전이가 갈라지고 상태별 행동이 재사용되는 구조가 생길 때
재검토한다.

## 검토 2 — 템플릿 메서드(Template Method)를 처리 루프에 적용?
항목 처리 6건은 이미 `_process_item()` 한 곳으로 공통화돼 있다. 여기에 "골격 + 훅"을 더
얹어봐야 갈라지는 변형이 없어 훅이 비어 있다. **결정: 적용하지 않는다.**

## 이미 실현된 패턴 — 미디에이터(Mediator)
새로 넣을 필요가 없는 이유: **중재 콘솔(`mediation.html` + `MediationRecord`)이 이미
미디에이터(Mediator) 패턴의 사례다.** 서로 직접 소통하지 않는 당사자(민원인/직원/감독원)들이
중재자(에이전트 「리걸메이트」)를 통해서만 쟁점·근거를 교환한다. 즉 이 프로젝트에서 Mediator는
백엔드 리팩토링 대상이 아니라 도메인 설계 자체에 들어와 있다.

## 결론
리팩토링은 Phase 1~4에서 실익이 있는 패턴만 적용하고 종료한다. 패턴은 목적이 아니라 수단이며,
맞지 않는 곳에 억지로 넣지 않는 것도 설계다.
