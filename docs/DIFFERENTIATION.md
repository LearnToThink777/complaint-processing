# 차별점 정리 — 챌린지 주제 대비 현재 프로젝트

> 챌린지 두 주제와 "시중은행 챗봇의 한계"에 현재 프로젝트(`complaint_processing`)를 대조하고,
> 이미 가진 차별점을 정리한 뒤 추가할 특화 차별점을 제안한다.

## 0. 한눈에

현재 프로젝트는 **"단일 오케스트레이터(상태 기계) + 역할별 LLM 스킬 7종 + 실코퍼스 RAG"** 구조다.
챌린지의 두 주제(멀티 에이전트 민원 작성 / 소비자 권익 보호 3-에이전트)를 **상당 부분 이미 충족**하고,
시중은행 챗봇 대비 **원리 수준의 차별점**(권한 경계·이중 공개·중립성 밸런스·근거 대조 검증)을 이미 갖추고 있다.
"멀티 에이전트"라는 표현과 "소비자 권익 보호 안내"만 **명시적으로 보강**하면 두 주제에 정확히 겹친다.

## 1. 챌린지 주제 ↔ 현재 프로젝트 대조

### 주제 ① 단계별 멀티 에이전트 기반 금융 분쟁 민원 작성 어시스턴트
| 챌린지 요구 | 현재 구현 | 상태 |
|---|---|---|
| 질의 분석 → 유사 판례·상담 사례 검색 | `retrieve_similar_cases()`(#3) + 분쟁조정 결정문 코퍼스 RAG (`retrieval.py`, law.go.kr 6,505청크) | ✅ 있음 |
| 보고서를 **단계별 자동 생성** | 20여 프레임을 상태 기계가 순차 생성(`agent.py::run`), 각 단계 `emit()` 스냅샷 | ✅ 있음(강점) |
| **역할 특화** 에이전트 | 단일 `ComplaintAgent` + task 7종(검토계획/판정/공개/유사사례/재협상/종결/색인라벨). 역할은 분리돼 있으나 "에이전트"로 명명·격상은 안 됨 | ⚠ 부분 |
| 검색 정확도·처리 효율 제고 | 일상어 라벨(`ChunkLabels.everyday_questions`)로 "돈 떼였어요↔손해배상" 비대칭을 색인 때 메꿈 | ✅ 있음(강점) |

### 주제 ② 금융 소비자 권익 보호를 위한 AI 에이전트
| 챌린지 요구 | 현재 구현 | 상태 |
|---|---|---|
| 분쟁 발생 시 **대응 절차·권리 보호 방안 안내** | 종결 시 `close_disclose()`가 결과를 안내하나, "소비자가 지금 행사할 수 있는 권리·다음 절차·기한"을 구조화해 주진 않음 | ❌ 없음(제안 대상) |
| 신뢰 제고 | 이중 공개·중립성 밸런스·권한 경계 고지문으로 신뢰 장치 다수 | ✅ 있음(강점) |
| **도메인 특화 3개 에이전트**(법률 / FAQ·민원사례 / 금융복합지식) | 법률(판정·검토계획)·사례(유사사례) 두 축은 있음. FAQ/일반지식 축은 약함 | ⚠ 부분 |

## 2. 이미 가진 차별점 (시중은행 챗봇 대비) — 잘 정리

말씀하신 "챗봇은 룰 기반·비개인화·키워드 매칭·메모리 없음"에 **정면으로 대응하는 설계가 이미 코드에 있다.**

1. **권한 경계 — 에이전트는 자문·중재만, 확정은 사람** *(가장 큰 원리적 차별점)*
   재협상 새 기한은 `recommended_new_due_date`로 **권고만**(`schemas.py::RenegotiationDraft.note`),
   중재는 최종 판단 주체를 항상 밖에 둔다(`MediationRecord.boundary`, `MediationIssue.decider`).
   → 말씀하신 "계좌 개설·서류 작성의 최종 주체는 인간" 우려를 **설계 원칙으로 이미 내장**.

2. **이중 공개(Dual Disclosure) — 청중별 재작문**
   같은 사실을 민원인용(법률어 없이 공감적)·감독원용(법조문·수치 포함)으로 나눠 쓴다
   (`schemas.py::DualDisclosure`, `agent.py::dual_disclose`). 은행 챗봇의 "모두에게 동일 답변"과 반대.

3. **중립성 밸런스 — 편향 없음을 계량**
   쟁점마다 `for_a/against_a/for_b/against_b`를 모두 채우고(`MediationIssue`),
   자문이 어느 쪽으로 기울었는지 집계(`AdvisoryBalance`). "저쪽 편 아니냐"는 의심에 근거로 답함.

4. **실코퍼스 RAG + 일상어 라벨 — 키워드 매칭이 아님**
   law.go.kr 법령·분쟁조정 결정문을 색인하고, 색인 시 LLM이 **일상어 질문 라벨**을 붙여
   민원인의 생활어와 법률 문서 사이 어휘 비대칭을 메운다(`schemas.py::ChunkLabels`, `retrieval.py`).

5. **동적 검토 계획 — 룰 기반 고정 메뉴가 아님**
   접수 전엔 체크리스트가 비어 있고(`agent.py` `self.checklist=[]`), 이관 시 사건 사실을 읽어야
   비로소 검토 항목을 **도출**한다(`ChecklistPlan`, `plan_checklist()`). → 개인화된(사건별) 검토.

6. **결정론적 오케스트레이션 ↔ LLM 판단 분리 — 감사가능성**
   원장 append·상태 전이·완결성 게이트는 상태 기계가, 판정·작문만 LLM이 담당(`agent.py` 도입부).
   각 단계가 프레임으로 스냅샷돼 **재현·감사 가능**(골든 테스트로 고정).

7. **출력 검증(Critic) — 할루시네이션 방어**
   산출물을 근거(law/facts)에 대조하고 BLOCK 시 산출 차단 가능(`decorators.py::CriticLLM`, `critic.py`).

8. **생애주기 연결 메모리(경량)**
   상담(중재)→처리(민원)를 `linked_case`로 잇고(`MediationRecord.linked_case`),
   처리 이력(`history`)·적용 법률 원장(`ledger`)이 사건 단위로 누적된다.
   → 세션 내 대화만 기억하는 챗봇과 달리 **사건 단위 이력**은 있음(단, 세션/사용자 간 영속 메모리는 아직 없음).

## 3. 말씀하신 "챗봇의 한계" 4가지에 대한 현재 위치

| 챗봇 한계 | 현재 프로젝트 | 판단 |
|---|---|---|
| 세션 대화만 기억(메모리 없음) | 사건 단위 이력/원장/생애주기 연결은 있으나, **사용자·세션을 넘는 영속 메모리는 없음** | 보강 여지 |
| 키워드 매칭·비개인화 | 실코퍼스 RAG + 일상어 라벨 + 사건별 동적 검토계획으로 **이미 개인화** | 강점 |
| 실행 기능(계좌 개설·서류 작성) 없음 | **의도적으로** 자문·중재만(권한 경계). 최종 결정은 사람 | 원칙(범위 밖으로 두는 게 타당) |
| 비(非)법률 일반 민원 처리 | 현재는 분쟁/법률 도메인에 집중. 일반 민원 **트리아지 없음** | 보강 여지 |

## 4. 추가 제안 — "조금 더" 특화 차별점 (택1 구현 권장)

이미 차별점이 많으므로, 챌린지 두 주제 중 **약한 칸(❌/⚠)을 메우는** 작은 특화 하나를 추가하는 걸 권한다.
셋 다 기존 계약(스키마/태스크/에이전트)을 **안 깨고 얹는 additive** 설계다.

### (A) ⭐ 소비자 권익 보호 안내 (Consumer Rights Guide) — 주제②의 핵심 공백 — ✅ 구현 완료
종결 시, **이 사건의 실제 원장·판정에 근거해** "지금 행사 가능한 권리 / 다음 대응 절차 / 기한 / 준비 서류 /
확대 경로(금감원 분쟁조정·소액소송)"를 구조화해 안내. 사건마다 다른 개인화된 안내(≠ 일반 FAQ).
- 구현: `schemas.py::ConsumerRightsGuide`·`RightsAction`, `tasks.py` `rights_guide`(mock+prompt),
  `agent.py::guide_rights()`(종결 단계에 배선), `presentation.py` frame `rights_guide`,
  `POST /api/skills/rights-guide` + `Frame.rights_guide`, `viewer.html` 권익 안내 패널.
- 개인화 증거: 원장에 위반이 있으면 위법계약해지·손해배상·분쟁조정 권리를, **무혐의면 권리 목록을
  접고** 일반 대응 경로만 안내(`tasks.py::_mock_rights_guide`, `tests/test_api.py` 검증).
- 매핑: 주제② "대응 절차·권리 보호 방안 안내" 정면 충족 + "비개인화" 비판 반박.
- 검증: 골든 재생성(`frames.json`) + `pytest` 통과(현재 16케이스) + 라이브 API/viewer 패널 확인.

### (B) 비법률 일반 민원 트리아지 (General Complaint Triage) — 말씀하신 "비법률 민원" — ✅ 구현 완료
접수 시 사건이 **법률 분쟁(legal)인지 / 단순 안내·행정 민원(general)인지**를 먼저 분류해, 후자는 경량 안내 경로로 분기.
- 구현: `ChecklistPlan.track`(legal/general), `GeneralGuidance` 스키마, `tasks.classify_track`(오프라인
  키워드 근사)+`general_guidance` 태스크, `agent.py::_run_general()`(경량 경로), `RetrievalLLM` #0 트랙 반영,
  `POST /api/skills/general-guidance` + `GET /api/frames?case=general`, viewer 트랙 배지·법률 패널 숨김·데모 토글.
- 안전망: general 처리 중 법률 소지가 보이면 `GeneralGuidance.escalation_hint`로 정식 민원 전환 안내
  (트리아지 오분류 방어). 애매하면 legal로(법률 분쟁을 일반 안내로 흘려보내지 않음).
- 매핑: 도메인 커버리지 확장 — "모든 민원을 법률 파이프라인에 밀어넣는" 구조를 벗어남.
- 검증: 골든 재생성 + `pytest` 16케이스(general 트랙 2건 포함) + 라이브 viewer 토글 확인.

### (C) 역할 특화 서브에이전트 명시화 (Role-Specialized Sub-Agents) — 주제①의 "멀티 에이전트"
기존 task 7종을 **LegalAgent / CaseAgent / CommunicationAgent** 3역할로 명명·그룹화해
"멀티 에이전트"를 명시적으로 드러냄(내부 배선은 대부분 유지, 얇은 파사드).
- 매핑: 주제① "역할 특화 에이전트" + 주제② "3개 에이전트" 문구에 직접 대응.
- 주의: 이득 대비 변경면적이 가장 큼(주로 명명·구조 정리).
